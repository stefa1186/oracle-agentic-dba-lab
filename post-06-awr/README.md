# Post 06 – Can an AI agent read an AWR report?

Runs a workload with two problems I choose in advance, between two AWR
snapshots, and gives the agent the AWR report with one question: what's wrong
with this database? Then checks every claim against the report.

Requires: posts 01-04 (database, SQLcl, the agent harness). The agent's
account is **not** changed: it reads the report attached to its prompt and
gets **no tools** (`--allow-tools NONE`), so this tests reading, not querying.

## The two planted problems

| Problem | How | What a DBA expects to see |
|---|---|---|
| Row lock contention | 1 session keeps row 1 of `AWR_LOAD.ACCOUNTS` locked for 5 s at a time; 4 sessions keep updating the same row | `enq: TX - row lock contention` at the top of the wait events |
| Hard parsing | 2 sessions run the same query on `AWR_LOAD.ORDERS` with a new literal every time | High `parse count (hard)`, `hard parse elapsed time` in the time model, a CPU-heavy profile |

All 7 are ordinary SQL*Plus sessions started side by side, logged in as the
application user `AWR_LOAD`, like a real application. Its password exists
only for one run: random, generated by `02`, passed to SQL*Plus through stdin
(never on a command line, never on disk), and the account is locked again
when the load ends, however it ends.

Why not scheduler jobs: the first version used them, and on this Free
database only 2 ran at a time (observed 2026-11-05, even with
JOB_QUEUE_PROCESSES raised to 9 in FREEPDB1), so a 3-minute load would have
taken 12 and measured something else. Sessions don't depend on the scheduler.

## Licensing

Oracle's *Database Licensing Information User Manual* (26ai) lists the
Diagnostics Pack (AWR, ASH, ADDM) as an **included pack for Oracle AI Database
Free**. On Enterprise Edition it's an extra-cost option. `01_check_awr.sh`
prints which edition you're on.

## Scripts (run as `oralab`, in order)

| Script | Purpose |
|---|---|
| `env.example` | Schema name, load duration, number of waiters and literal-SQL sessions |
| `lib.sh` | Reuses posts 01-04 helpers; runs this folder's SQL files with their settings |
| `01_check_awr.sh` | Read-only: Diagnostics Pack access, STATISTICS_LEVEL; licensing note |
| `02_generate_load.sh` + `setup_load.sql`, `snapshot.sql`, `session_*.sql` | The application user and its tables, BEGIN snapshot, the 7 workload sessions (3 minutes by default), END snapshot, account locked. Saves `snapshots.txt` and one log per session (`sessions/`) |
| `03_awr_report.sh` + `awr_report.sql` | The AWR text report (`awr_report.txt`, what the agent reads), the same report without ADDM's sections (`awr_report_noaddm.txt`, checked: no "ADDM" left), and the answer key from DBA_HIST (`answer_key.txt`) |
| `04_prompt.md` | The question, the rules (quote every line you rely on), the answer format |
| `05_check_claims.sh` + `check_claims.py` | Is each quote really in the report? Which numbers aren't? Were both problems found? Writes `scorecard.md` |
| `99_cleanup.sh` | Ends any leftover workload session, drops `AWR_LOAD`. Keeps snapshots and evidence |

## Step by step

```bash
cd ~/oracle-agentic-dba-lab/post-06-awr
./01_check_awr.sh
./02_generate_load.sh          # about 3-4 minutes
./03_awr_report.sh

# The agent: the report attached, no tools, one answer.
cd ../agent-harness
./run_matrix.sh ../post-06-awr/04_prompt.md -- \
    --attach ~/oracle-agentic-dba-lab/output/post-06-awr/awr_report.txt \
    --allow-tools NONE
cd ../post-06-awr

./05_check_claims.sh           # the latest run

# The harder test: the same report without ADDM's own diagnosis.
cd ../agent-harness
./run_matrix.sh ../post-06-awr/04_prompt.md -- \
    --attach ~/oracle-agentic-dba-lab/output/post-06-awr/awr_report_noaddm.txt \
    --allow-tools NONE
cd ../post-06-awr
./05_check_claims.sh           # checked against the report that run read
./99_cleanup.sh                # when done
```

Every model in a matrix reads exactly the same report (its SHA-256 is in each
run's `events.jsonl`), so differences come from the model alone.

## How claims are checked

The prompt asks for every finding as

```
FINDING | <the problem> | <the report section> | <the line from the report, copied exactly>
```

`check_claims.py` then checks, mechanically:

1. **Grounding:** is the quoted line in the report (whitespace aside)? If
   not, is there one report line holding all its numbers? If neither, the
   suggested mark is 👻.
2. **Numbers:** every number in the whole answer that appears nowhere in the
   report. Some will be the agent's own arithmetic, so these are for review.
3. **Planted problems:** which findings mention each one, and at which rank.

Whether a correctly quoted line leads to a correct conclusion (✅ or ⚠️)
needs a DBA reading the report. That mark is mine, in `scorecard.md`.

## Things to watch

- **Report size.** `03_awr_report.sh` prints the report's length and a rough
  token estimate. If a model's context window is smaller, the request fails
  and the run log says so: that's a result too.
- **Leftover sessions.** If `02` stops early or a session overruns its
  deadline, its exit trap kills the workload's database sessions and locks
  the account; `99_cleanup.sh` does the same.
- **Rerunning** `02` kills and drops the previous workload first; the new
  snapshot pair replaces `snapshots.txt`.

## Observed on the lab (2026-11-05, nvidia/nemotron-3-ultra-550b-a55b:free)

- **Load:** snapshots 14-15, 7 sessions, 531,200 literal executions;
  `enq: TX - row lock contention` 65.4% of DB time; 535,743 of 549,110
  parses hard; `resmgr:cpu quantum` present (Free's CPU limit).
- **Report:** 4,353 lines, 250,823 characters; 74,472 tokens in the call.
- **Answer:** 13 findings, both planted problems found and ranked correctly,
  no number missing from the report. Marks: 11 ✅ (9 evidence lines for the
  two problems, 2 for ADDM's minor soft-parse finding), 2 ⚠️ (dictionary
  cache misses: a symptom of the hard parsing; ADDM's own run reported as
  "AWR repository maintenance generating significant load").
- **Caveat:** the 26ai AWR report includes ADDM's findings, which name both
  planted problems. The agent's first findings quote them. Hence
  `awr_report_noaddm.txt`: the findings block, the table-of-contents entry
  and the ADDM Reports section removed (lines 28-36, 180, 4143-end in this
  report), the harder test.
- **check_claims.py:** two quotes were real lines from different places
  glued together; reported as "stitched", not "not in report", since then.
- **Run 2, no ADDM** (`awr_report_noaddm.txt`, 4,108 lines, 245 removed):
  71,763 tokens in, 40 findings, all quotes verbatim. Both problems found
  and ranked correctly from the raw numbers; the cause (literals, no bind
  variables) never named. Marks: 21 ✅, 17 ➖ (true, not problems), 2 ⚠️
  (recursive calls blamed on dictionary lookups; "(up to 2 min)" read as
  the wait duration), 0 👻. The 4 numbers not in the report were its own
  rounding; `check_claims.py` lists rounded/truncated numbers apart since.
- **Fairness note:** the workload sessions set MODULE to "post06 workload",
  visible in the report. A neutral name would be cleaner for future runs.
